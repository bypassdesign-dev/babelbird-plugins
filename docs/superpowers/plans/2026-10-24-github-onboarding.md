# GitHub installation and local API Key setup

The user approved a local, single-field API Key page and authorized implementation, validation and GitHub publication. This extends that approved design across confirmed host formats.

## Acceptance

- One natural-language instruction with the GitHub link tells the installing agent to clone the current release, choose its own host, install both skills and start the local page.
- The page opens automatically, shows the selected host, supports Chinese and English, accepts only an API Key, performs the real personal-folder read check and saves a user-level connection. No key enters chat or project files.
- Installation is idempotent. Existing connections and unrelated config survive; another account receives a new server name.
- Codex and WorkBuddy are priority targets. Additional adapters require primary-source confirmation of config and skill locations. The support matrix distinguishes fixture checks, native parser checks and actual agent end-to-end checks.
- Cloud bindings, no-ZIP project sync, quota skipping and POSIX permissions retain their existing behavior.

## Implementation sequence

1. Confirm installed WorkBuddy loader and current official formats for other hosts. Record sources and version-dependent products.
2. Add host descriptors, additive private JSON/JSONC config updates, cross-host launcher and installer; retain the old Codex entry point.
3. Extend the approved form with host-specific completion text and browser-language Chinese/English text. Keep exactly one credential input.
4. Make installed skills self-contained; update bilingual install instructions and the support matrix.
5. Run regression, malformed-config, collision, permission, installer and page tests. Observe the page in a browser. Run real read-only BabelBird verification and native Codex/WorkBuddy loader checks in isolated homes.
6. Review final diff and package, publish a GitHub prerelease and verify published content. No official-market submission in this task.

## Validation limits

Full app/agent verification requires the product to be installed and authenticated. Config fixtures and direct MCP requests do not prove the host loaded the tools. Record limits per product.
